# Генератор платёжного QR: KMP + нативный iOS UI

Документация для реализации собственного клиента на основе нашего исследования X5 / «Перекрёстка» / «Апельсина». Подготовлена 30.10.2026. Протокол зафиксирован по APK 4.0.0 и 4.1.1, iOS-трафику 4.1.0 и эксперименту регистрации 28.10.2026 МСК.

Целевая архитектура: **KMP формирует протокольные сообщения, платформенный криптографический код подписывает их, SwiftUI отображает QR**. Нативный интерфейс iOS можно разрабатывать независимо от Android.

## Как читать

1. [PROTOCOL.md](PROTOCOL.md) — точные поля, байты, подписи, идентификаторы и форматы ключа.

5. [TESTING.md](TESTING.md) — эталонные данные и критерии готовности реализации.

Начать стоит с **офлайн-MVP через импорт существующей привязки**. Для генерации QR ему не нужны OAuth, Bearer, x-sign, банк или X5 API. Сетевое подключение нового устройства — отдельный следующий этап.

## Что уже доказано

| Результат | Основание |
|---|---|
| ECDSA P-256 / SHA-256, формат r || s | Проверка захваченного iOS QR и собственных подписей |
| Порядок полей QR и банковского fingerprint | Код Android SDK и расшифрованные QR |
| Преобразования версий и код модели | Код SDK; совпадение iPhone16,1 → 1PPnA и Xiaomi 22101320G → 2Wl0P |
| Формула Android AppUserUUID | Код SDK в двух версиях APK; воспроизведённая реализация |
| Регистрация своей пары ключей | X5 Success; банк orangePayEnabled / appInstanceRegistered |
| Преобразование fingerprint в P1363 перед отправкой в банк | Код JS-моста; исправление первого отказа 409036 и успешное подтверждение |

Последний зафиксированный key_id нашего генератора — **85898710**, valid_until — **2027-10-28**. Это исторический результат регистрации, не свежая проверка активности.

## Что остаётся неизвестным

- Приём нашего QR кассой: покупка для проверки не выполнялась.
- Срок принятия QR, защита от повторного предъявления и точный порядок проверок сервера.
- Внутренняя формула AppUserUUID нативного iOS SDK: разобранная формула относится к Android. Наш KMP-клиент может явно реализовать этот Android-compatible профиль.
- Полная обязательность x-sign на разных API. GET списка карт работал и без него.
- Полный самостоятельный OAuth/refresh сценарий нового KMP-приложения.

Не переносить `ttl=300` из GET /barcode на этот QR: это другой формат серверного кода.

## Что входит в пакет

```text
reference/
  commonMain/
    QrProtocol.kt             # WireProfile, сообщения QR/fingerprint, сборка envelope
    DerCodec.kt               # строгий DER ↔ P1363 для P-256
    IdentityDerivation.kt     # model_id и Android-compatible AppUserUUID
    KotlinCryptoBlake2b.kt    # адаптер BLAKE2b для commonMain
  commonTest/
    QrProtocolTest.kt         # тесты для целевого shared-модуля
  ios/
    P256Signer.swift          # CryptoKit, Keychain, UTC formatter
    QRRenderer.swift          # Core Image, белая рамка, целочисленный масштаб
    PaymentQrScreen.swift    # отдельный компонент SwiftUI, iOS 17+
    KmpQrSource.swift         # место соединения Shared.framework и Swift
  fixtures/
    vectors.json
    TEST-ONLY-private.pem
    TEST-ONLY-public.pem
```

Это документация и исходники для переноса в твой проект, **не готовый Gradle/Xcode-проект**. Состояние реального аккаунта, активный приватный ключ, seed, Bearer и клиентские секреты в пакет не включены. Ключ в fixtures — открытый тестовый ключ с известным всем скаляром d=1; он предназначен только для тестов.

Границы выполненных проверок приведены в [TESTING.md](TESTING.md). Kotlin/Native framework и реальный iOS-приложение нужно собрать и проверить в целевом проекте.

## Порядок реализации

1. Подключить shared-модуль и перенести QrCodec + DerCodec. Подписывать пока тестовым ключом.
2. Прогнать vectors.json на Kotlin и CryptoKit; добавить отрицательные проверки.
3. Подключить P256Signer и репозиторий привязки, реализовать явный импорт существующего ключа.
4. Сделать SwiftUI-экран поверх QrPayloadSource: новый QR при открытии, возврате в foreground и по кнопке.
5. Сравнить распознанную строку из картинки с подписанной строкой; проверить подпись публичным ключом.
6. Отдельно реализовать login/onboarding нового устройства, если он нужен.
7. Провести согласованную проверку на кассе и только после неё уточнять серверные правила свежести.
