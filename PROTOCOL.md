# Спецификация сообщения и криптографии

Это описание наблюдаемого формата. Рекомендации по архитектуре и UI вынесены в [KMP-IOS.md](KMP-IOS.md), подключение банка — в [ONBOARDING.md](ONBOARDING.md).

## 1. Основная операция

```text
message      = join(fields, ";")
messageBytes = UTF8(message)
signature    = ECDSA_P256_SHA256(privateKey, messageBytes)
signature64  = r[32 bytes, big-endian] || s[32 bytes, big-endian]
payload      = message + "." + lowercaseHex(signature64)
QR image     = QR_Encode(UTF8(payload))
```

Точка и hex-подпись не входят в messageBytes. Пробелы, перенос строки, BOM, кавычки JSON и завершающий NUL не добавляются. Это подпись открытого текста: содержимое QR читается обычным сканером.

При декодировании отделять подпись **по последней точке**: полное имя модели в fingerprint потенциально может содержать точки. Для QR все девять полей соединяются без завершающего `;`.

ECDSA может выдать разные корректные подписи для одинакового message. В тестах сравнивать сообщение и проверять подпись, а не требовать равенства двух новых подписей.

## 2. Поля платёжного QR

| № | Поле | Правило |
|---|---|---|
| 1 | card_number | Номер карты лояльности; в наблюдаемых данных 16 ASCII-цифр |
| 2 | issued_at | UTC, `yyyyMMddHHmmss`, ровно 14 ASCII-цифр |
| 3 | key_id | Положительный десятичный ID из ответа X5, без форматирования/разделителей |
| 4 | phone | 10 цифр российского номера, без 7/+7/8 |
| 5 | user_app_id | AppUserUUID, 32 lowercase hex-символа |
| 6 | short_os | Цифры версии ОС, первые максимум 3 |
| 7 | short_merchant | Если merchant длины 2 — первый символ; иначе последний |
| 8 | app_version | Цифры версии приложения, первые максимум 5 |
| 9 | model_id | Код модели: 5 символов Base62 |

Далее — точка и подпись из 128 hex-символов. Полный синтетический образец — `reference/fixtures/vectors.json`, поле payment_qr.

В наблюдаемом Android-профиле:

```text
osVersion   = "14"                  → "14"
appVersion  = "4.1.1"               → "411"
merchant    = "TCX"                 → "X"
modelName   = "Xiaomi 22101320G"     → "2Wl0P"
```

Для iOS-образца `27.2 → 272`, `4.1.0 → 410`, `iPhone16,1 → 1PPnA`.

**Не брать версию нового UI-приложения автоматически.** WireProfile — набор данных протокола, связанный с выбранной привязкой. UiEnvironment — реальная текущая ОС/версия/модель для интерфейса и диагностики. При импорте уже зарегистрированного профиля сохранять исходный WireProfile.

## 3. Полный банковский Device-Fingerprint

```text
issued_at;phone;user_app_id;short_os;short_merchant;app_version;model_id;model_name
```

Подписывается той же парой ключей. Envelope тот же: `message + "." + hex(r32 || s32)`.

В fingerprint нет card_number и key_id. Полное имя модели занимает последнее поле. Fingerprint формировать непосредственно перед auth/confirm, а не при открытии OTP-экрана за несколько минут до отправки.

Подпись в DER вместо P1363 привела в нашем эксперименте к HTTP 409 / error_code 409036 «Слепок устройства не валиден». Последующее преобразование в r || s устранило конкретно эту ошибку. Этот код ошибки сам по себе не доказывает, что любая будущая ошибка fingerprint вызвана только DER.

## 4. Подпись P-256 и форматы

Кривая: secp256r1 / NIST P-256 / prime256v1. Digest: SHA-256. Не подменять secp256k1.

| Значение | Формат | Размер |
|---|---|---|
| Подпись в QR / Device-Fingerprint | IEEE P1363: r32 || s32 | 64 байта, 128 hex-символов |
| Подпись Java Signature / OpenSSL | ASN.1 DER SEQUENCE(INTEGER r, INTEGER s) | Длина переменная |
| Публичный ключ в X5 JSON | SEC1 uncompressed: 04 || x32 || y32 | 65 байт, 130 hex-символов |
| Публичный ключ в банковском Public-Key | SPKI DER | 91 байт для используемого named-curve P-256 формата |

SPKI для этого формата:

```text
3059301306072a8648ce3d020106082a8648ce3d030107034200
+ 04 || x32 || y32
```

DER INTEGER — положительное целое: при установленном старшем бите добавляется ведущий 00. Обратно в P1363: убрать только знаковый ноль, дополнить слева до 32 байт. Нельзя просто взять последние 64 байта DER.

Проверка подписей использует тот же SHA-256 и исходный messageBytes. В CryptoKit вызывать `signature(for: Data(message.utf8))`: этот overload уже хеширует данные. В Android `SHA256withECDSA` тоже получает исходное сообщение. Двойного SHA-256 быть не должно. [Apple API](https://developer.apple.com/documentation/cryptokit/p256/signing/privatekey), [Android Signature/Keystore](https://developer.android.com/privacy-and-security/keystore).

## 5. Код модели

1. Преобразовать modelName в UTF-8 без изменения регистра и пробелов.
2. Вычислить BLAKE2b, указав длину результата **4 байта**.
3. Считать результат беззнаковым big-endian целым.
4. Записать в Base62: `0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz`.
5. Если длина меньше 5, повторить шаги 2–4 с выходом **5 байт**.
6. Взять первые 5 символов.

Нужен параметризованный BLAKE2b: `BLAKE2b(outputBytes * 8)`. Усечение BLAKE2b-512 даст другой результат. В reference используется [KotlinCrypto BLAKE2b](https://github.com/KotlinCrypto/hash/blob/master/library/blake2/src/commonMain/kotlin/org/kotlincrypto/hash/blake2/BLAKE2b.kt); параметр конструктора задаётся в битах.

В тестовых данных есть редкая ветка fallback — SyntheticModel-51.

В Android SDK modelName формируется из manufacturer/model: если model уже начинается с manufacturer без учёта регистра, используется model; иначе manufacturer + пробел + model. Первая буква итогового значения приводится к заглавной. Для нашего телефона получилась строка Xiaomi 22101320G. Для исходного iPhone наблюдалась аппаратная строка iPhone16,1. На iOS `UIDevice.model` обычно не даёт именно эту аппаратную строку; для новой привязки строку модели нужно определять отдельно и тестировать. Для импорта используется уже сохранённая строка.

## 6. Три ID и seed

### mobile_device_id

UUID клиента, передаваемый при регистрации публичного ключа и в X5-заголовках. Не выводится из модели или телефона. Создаётся и сохраняется один раз для выбранной новой привязки. При импорте сохраняется существующее значение.

### key_id

Назначается X5. Его нельзя выбирать локально, брать от старой пары или заменять на user_app_id. После создания другого ключа старый key_id не превращает его подпись в подпись зарегистрированной пары.

### user_app_id / AppUserUUID

Android-compatible формула:

```text
seed_string = uppercaseHex(16 random bytes)
x5id_hex    = lowercaseHex(UTF8(decimal X5ID))
pub_sdk     = sdkPublicString(publicKey)

user_app_id = lowercaseHex(
    BLAKE2b(outputBytes=16, UTF8(seed_string + x5id_hex + pub_sdk))
)
```

Вход хеша — ASCII-строки, склеенные без разделителя, не конкатенация исходных seed/key байтов. Seed нельзя регенерировать на каждом запуске. X5ID — ID аккаунта, не номер телефона.

`sdkPublicString` намеренно воспроизводит особенность Android SDK:

```text
xBytes = Java positive BigInteger(x).toByteArray()
yBytes = Java positive BigInteger(y).toByteArray()
buffer = 65 нулевых байт
buffer[0] = 04
copy first 32 xBytes → buffer[0..31]    # перезаписывает 04
copy first 32 yBytes → buffer[33..64]
buffer[32] остаётся 00
pub_sdk = lowercaseHex(buffer)
```

При координате со старшим битом Java добавляет знаковый ноль, поэтому копирование первых 32 байт отличается от обычной нормализации x/y. Если Java-представление короче 32 байт, оригинальная логика не срабатывает; reference возвращает ошибку. При генерации ещё не зарегистрированного ключа допустимо создать другую пару до фиксации seed/ID; уже зарегистрированный ключ по этой причине не заменять.

Это правило используется **только во входе хеша AppUserUUID**. В X5 и банк отправляется правильный публичный ключ. Сохранённый user_app_id у импортированной привязки проверяется по профилю derivation; его нельзя пересчитать другой формулой «для удобства».

## 7. Время и обновление

- Использовать UTC и Gregorian calendar. Пример: `20261027220000`.
- Локаль, пользовательский 12-часовой формат и часовой пояс UI не влияют на строку.
- В Swift формат `yyyy`, не `YYYY`: последнее означает week-based year.
- Система должна давать корректное текущее время. Если проект применяет поправку серверного времени, источник, TTL поправки и ошибка часов должны быть явной политикой.
- Новый QR при открытии экрана, возвращении приложения в foreground и нажатии «Обновить».
- Автообновление, например раз в 30 секунд, — только выбранная политика интерфейса. Это не установленный TTL сервера. В reference авто-таймер отсутствует.
- Не показывать «действует ещё 300 секунд»: оснований для этого нет.

## 8. Проверка результата

1. Декодировать PNG/CGImage обычным QR-декодером.
2. Сравнить полученную строку с payload побайтно.
3. Отделить подпись по последней точке, распарсить hex, проверить длину 64.
4. Проверить ECDSA/SHA-256 публичным ключом выбранной привязки.
5. Проверить, что key_id / user_app_id взяты из этой же привязки.

Криптографическая проверка не устанавливает текущий банковский статус, срок принятия QR и факт оплаты. Эти уровни отображать и тестировать отдельно.
