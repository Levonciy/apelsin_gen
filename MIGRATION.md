# MVP: перенос уже зарегистрированной идентичности

Цель — получить офлайн-экран QR на iOS без повторной регистрации. Существующая привязка создана нашим генератором на Mac; её ключ доступен нам. Мы не извлекаем ключ официального iOS/Android-приложения.

## 1. Существующие данные

В рабочей папке исследования находятся:

```text
work/local-generated-android/private.pem
work/local-generated-android/state.json
work/local-generated-android/public.pem
```

Состояние регистрации, зафиксированное 28.10.2026 МСК: key_id=85898710, user_app_id=6621b489e6e88519f92d9902cab830a0, Android-compatible WireProfile Xiaomi 22101320G / Android 14 / app 4.1.1. Это не свежий запрос статуса на дату чтения документа.

Активный ключ и state.json намеренно не продублированы в документацию. Их не добавлять в исходники приложения или Git. Fixtures содержат другой, публичный тестовый ключ.

## 2. Что переносится вместе

| Значение | Действие |
|---|---|
| private key | Импортировать в Keychain; проверить соответствие public key |
| public key SEC1/SPKI | Сверить обе формы с импортированным private key |
| key_id | Сохранить без замены |
| user_app_id | Сохранить без пересоздания |
| mobile_device_id | Сохранить для будущих API-запросов |
| seed + derivationProfile | Сохранить как часть идентичности, если переносится полный bundle |
| номер карты и телефон | Сохранить точно в wire-формате |
| модель, версии, merchant/model_id | Сохранить исходный WireProfile |
| keyValidUntil / последний статус | Сохранить как сведения о предыдущей проверке |

Красивый SwiftUI-интерфейс не требует менять поля Android-compatible WireProfile на реальные значения iPhone. Если решено создать новую iOS-идентичность с иным ключом/профилем, это уже [новая регистрация](ONBOARDING.md).

## 3. Предлагаемый import bundle

Пример структуры, **без реальных значений ключа и пользователя**:

```json
{
  "schema_version": 1,
  "derivation_profile": "android-sdk-v1",
  "private_key_pem": "<PKCS#8 PEM>",
  "public_key_sec1_hex": "<130 hex>",
  "public_key_spki_hex": "<182 hex>",
  "mobile_device_id": "<UUID>",
  "x5id": "<account ID, decimal>",
  "user_app_id": "<32 lowercase hex>",
  "installation_seed_upper_hex": "<32 uppercase hex>",
  "key_id": "<positive decimal>",
  "wire_profile": {
    "card_number": "<16 digits>",
    "phone10": "<10 digits>",
    "os_version": "14",
    "merchant": "TCX",
    "app_version": "4.1.1",
    "model_name": "Xiaomi 22101320G",
    "model_id": "2Wl0P"
  },
  "key_valid_until": "2027-10-28"
}
```

Формат JSON приложения — предлагаемый, а не формат сервера X5. Реальные state.json/private.pem нужно явно преобразовать в этот контракт. Нет необходимости включать Bearer или refresh token: ежедневная офлайн-генерация их не использует.

## 4. Алгоритм импорта

1. Пользователь явно выбирает файл импорта. Не регистрировать новую пару, если файла нет.
2. Проверить schema_version, ограничения размера, обязательные поля и допустимые символы.
3. Загрузить PEM через P256.Signing.PrivateKey(pemRepresentation:).
4. Получить publicKey.x963Representation и publicKey.derRepresentation; сравнить с bundle. При несовпадении импорт отклонить.
5. Проверить WireProfile через QrCodec. Проверить model_id из model_name.
6. Для android-sdk-v1 проверить AppUserUUID по seed, X5ID и ключу. Если импортируется минимальная legacy-привязка без seed/X5ID, использовать отдельный derivationProfile imported-existing и отметить derivation-check как невыполненный; X5ID нельзя выдумать из телефона.
7. Создать staging-запись ключа и metadata. Убедиться, что активная привязка ещё не перезаписана.
8. Подписать тестовое локальное сообщение, проверить подпись полученным public key.
9. Атомарно переключить activeBinding на полностью сохранённую staging-запись; удалить временные копии импортного файла согласно политике приложения.
10. Создать свежий QR, распознать и проверить его в dev-сборке. Показать дату последнего известного банковского статуса отдельно.

Reference P256Signer проверяет PEM/SPKI и запрещает перезапись alias, но сам не реализует весь staging/commit. Вариант целостного хранилища: один защищённый Keychain blob для всего bundle либо транзакционные metadata + журнал keyRef. Выбрать и протестировать восстановление после сбоя между сохранением ключа и metadata.

## 5. Что импорт не делает

Импорт не вызывает PUT /qr-public-key, customer/auth или auth/confirm. Не создаёт новый user_app_id. Не обновляет lastStatusCheckedAt без сетевой проверки. Не утверждает, что банк разрешает одновременное использование одного ключа на нескольких физических устройствах: такой сценарий отдельно не проверялся.

При переносе получается та же зарегистрированная криптографическая идентичность с другим локальным хранилищем. Поведение сервера после переноса на iOS и кассовый приём остаются предметом end-to-end проверки.

## 6. Восстановление и ротация

- Потеря доступа к Keychain: KeyUnavailable, а не автоматическая генерация другой пары.
- Другой private key при прежнем key_id: ошибка конфигурации.
- Изменение seed при прежнем user_app_id: несогласованная идентичность.
- Восстановление на другом iPhone при ThisDeviceOnly: ключ не мигрирует автоматически; нужен предусмотренный пользователем импорт/backup либо новая регистрация.
- Переход на Secure Enclave: новый ключ и явная новая привязка, сохранить существующий PEM внутри SE нельзя.

Удаление локальных данных и отзыв банковской регистрации — разные операции. В интерфейсе они должны быть названы отдельно.
